## 재현된 결함

### F1 · P1 — 관측 간격에 점프 시작이 끼면 수직속도가 틀리고 소수가 물리 시뮬레이션에 들어간다

위치: [estimateMyVy, 1364행](C:/leonyi-bot/reports/final-review-20260905/source/Lion_Eating_Bank_v12_1.js:1364), [me0.vy 사용, 1656행](C:/leonyi-bot/reports/final-review-20260905/source/Lion_Eating_Bank_v12_1.js:1656).

`dy / d + (d + 1) / 2`는 두 관측 사이 전체 구간에서 같은 점프 궤도를 따를 때의 식이다. 구간 중간에 점프를 시작하면 지상에 있던 프레임까지 포함해 나눠 버린다. 실게임 tick 27에서 self.y=213, state=1인 첫 점프 관측은 실제 vy=-14지만 함수는 -8.333333333333334를 반환했다. 이 값은 평가 점수가 아니라 `microSim`/`microSimSeq`의 물리 상태 초기값으로 사용된다. 이후 예측 높이·접촉 시점·공중 공격 점수가 달라질 수 있다.

실게임 4개에서 공중 관측 1,399건 중 엔진 속도와 불일치 155건(11.08%), 소수 반환 145건(10.36%)을 기록했다. 이는 해당 표본의 추정 오류 빈도이며 패배율 또는 전체 경기의 오류율을 뜻하지 않는다. 일부 관측은 Thunder가 최종 액션을 담당하는 동안의 AC 추정이다.

수정 방향: 점프·착지 전환과 적용 지연을 반영한 정수 궤도 복원, 또는 검증된 self 추적 상태를 초기값으로 사용한다. 단순 반올림은 -8.33을 -8로 바꿀 뿐 실제 -14를 복원하지 못한다. 수정 후 첫 점프·연속 점프·틱 누락·랠리 초기화에 대해 엔진 값과 비교한다.

증거: [velocity-audit.json](evidence/velocity-audit.json), [재현 검사](repro/velocity-audit.mjs).

### F2 · P1 — y=244인 프레임을 한 프레임 일찍 착지 처리한다

위치: [microSim, 697행](C:/leonyi-bot/reports/final-review-20260905/source/Lion_Eating_Bank_v12_1.js:697), [microSimSeq, 751행](C:/leonyi-bot/reports/final-review-20260905/source/Lion_Eating_Bank_v12_1.js:751). 대조: [공식 엔진, 606행](C:/leonyi-bot/reports/final-review-20260905/source/official-physics.js:606).

후보는 `futureY < 244`가 아니면 즉시 vy=0·지상 상태로 바꾼다. 공식 엔진은 `futureY > 244`일 때만 착지하며, 정확히 244인 프레임은 기존 속도와 공중 상태를 유지한다.

재현 입력: self=(x100,y228,vy16,state1), ball=(x120,y212,vx0,vy0), action={x:0,y:0,hit:1}. 공식 엔진은 y=244에서도 파워히트가 가능해 ball=(vx10,vy0), state=2가 된다. 두 예측기는 이를 보통 접촉으로 계산하며 `powerTouches=0`; 단계 예측기의 공은 (vx6,vy-15)다. 실제 가능한 공격을 버리거나 착지·터치 계획을 잘못 평가할 수 있다.

수정 방향: 두 함수의 착지 분기를 엔진의 엄격한 `>` 조건에 맞추고, 상태/속도/애니메이션 갱신 순서를 함께 대조한다. 243·244·245 경계에서 hit/up 입력을 교차해 검증한다. 두 함수 중 하나만 고치면 예측기 사이의 불일치가 남는다.

증거: [probes.json의 exactLanding](evidence/probes.json), [재현 검사](repro/audit-probes.mjs).

### F3 · P2 — 누운 상대를 접촉 불가능한 것으로 모델링한다

위치: [kgOppMotion, 479행](C:/leonyi-bot/reports/final-review-20260905/source/Lion_Eating_Bank_v12_1.js:479).

state=4일 때 초기 프레임의 도달 높이를 `ys: []`로 반환한다. `kgOppCanReach`는 빈 배열이면 접촉 검사를 건너뛴다. 그러나 입력을 받을 수 없는 동안에도 누운 플레이어의 몸은 공과 충돌한다. self/상대 몸=(x100,y244,state4), ball=(x120,y230)인 다음 프레임에서 실제 엔진은 범프(vx6,vy-15)를 발생시키지만 도달 판정은 false였다.

일반 공개 스냅샷에는 lyingDownDurationLeft가 없고 함수는 이를 0으로 간주한다. 그 경우에도 첫 프레임을 누락하는 구조다. 여러 프레임의 궤적에서는 나중 접촉 가능성 때문에 false가 가려질 수 있으므로, 모든 실제 공격이 잘못된 킬 판정으로 이어진다고 단정하지 않는다.

수정 방향: 행동 가능 시점과 몸 접촉 가능성을 분리한다. 눕는 동안에는 이동량 0과 실제 몸 높이를 유지하고, 일어난 뒤에만 보행·점프 선택지를 허용한다.

증거: [probes.json의 lyingContact](evidence/probes.json).

### F4 · P1 — 제출 게이트가 항상 null을 반환하는 봇도 승인한다

위치: [rule_check.mjs, 59행](C:/leonyi-bot/reports/final-review-20260905/source/rule_check.mjs:59). 후보 런타임 결함과 별개인 검증 도구 결함이다.

`if (a !== null && !valid(a))` 때문에 null을 비정상 반환으로 세지 않는다. `function decide(){return null;}`을 실제 게이트에 넣으면 `throws 0 invalid 0`, “게이트 전부 통과 → 제출 가능”, 종료 코드 0을 출력했다. 어댑터가 없는 파일은 SK 테스트도 생략하는 정상 경로가 있어 이 누락을 다른 검사에 맡길 수 없다. 후보 자체는 별도 벤치마크의 null 포함 반환 검사에서 비정상 반환 0이었다.

수정 방향: null을 포함한 계약 위반을 모두 세고, 검사 실패를 종료 코드로 전달한다. 어댑터 내부 오류 카운터도 점검한다. null·undefined·NaN·범위 초과·throw의 실패 주입 테스트로 게이트가 실제 실패하는지 확인한다. 부수적으로 `gates.mjs`의 `/decide: .*$/m`는 성능 행 대신 `top-level decide: yes`를 먼저 잡아 소요시간 요약을 숨기므로 행 시작을 고정해야 한다.

증거: [실제 게이트 출력](evidence/null-gate-output.txt), [실패 주입 파일](repro/NullReview_v1.js).

## 벤치마크

기존 제공 `RealGame`/`BotInput` 하네스에 위 공식 엔진을 연결했다. 새 엔진/하네스를 작성하지 않았다. 상대별 시드 20개를 좌우 교환해 40경기, 경기마다 새 봇 인스턴스, 지연 1프레임, 10점 선취다. 본시험은 25fps 기준 시간을 사용하며 슬로모션 프레임의 5배 시간 비용을 포함했다. 4분 시점 점수 우위로 판정하고 동점이면 골든볼, 최대 5분으로 종료했다. 실제 운영 서버의 전체 대회를 실행한 것은 아니다.

약한 세 상대에는 확실히 우세하다. v11에는 득점 점유율 48.57%, v12에는 50.00%로 개선을 입증하지 못했다. 강한 두 상대의 모든 경기가 시간 규칙에 도달했으므로 10점 완주 40경기 결과처럼 해석하면 안 된다. 현재 SK.on=false에서 v12와 출력이 동일한 것은 회귀가 없다는 근거이며 실력 향상의 근거는 아니다.

- 공 단독 월드 이동: 벽·천장·네트·착지와 vy=-80,-41,-40,-39,0,39,40,41,80을 포함한 100,000건에서 불일치 0. 선수 접촉을 제외한 검사이고, 착지 종료 프레임은 반환값과 착지 x를 비교했다. 후보가 종료 후 더 쓰지 않는 y까지 동일하다고 주장하지 않는다.
- 공식 엔진은 공 이동 전에 수직속도를 ±40으로 제한한다. 후보의 공 이동은 이에 맞았다. 로컬 `docs/CONTRACT.md`의 이동 순서에는 이 제한이 빠져 있으므로 문서 보완이 필요하다. 기존 `C:/leonyi-volleyball`도 같은 공식 커밋이었다.
- 제공 제출 게이트: 정적 로드 통과, v12 대비 2,269회 출력 불일치 0, SK S1~S6 통과, builtin 4경기 4승, 예외/비정상 반환 0. 다만 F4 때문에 게이트 통과 문구 자체는 최종 승인 근거로 부족하다.
- Thunder: builtin/NetCamper, 시드 101/202/303, 좌우 12경기에서 활성 틱 1,493개, 테이블 항목 80/80, 예측 불일치 0, selfcheck abort 0. 이 검사는 현 엔진에서의 고정 패턴을 지지한다.
- 미러 출력: NetCamper 궤적 1,918회는 불일치 0. v12 상대의 긴 궤적 8,000회에서는 158회 불일치였다. v12 동일 정책 자기대전에서도 후보 왼쪽 득점 점유율 65.71%, 오른쪽 34.29%로 로컬 45~55% 기준에서 벗어난다. 시드가 짝지어져 있으므로 40개의 독립 표본처럼 해석하지 않는다. 네트 정중앙에서 공식 엔진 자체의 반사 방향 비대칭 등이 섞일 수 있어 봇의 단순 tie-break 결함이라고 단정하지 않는다. 원인을 분리해 재검증해야 한다.
- `tickFrameGroupSize`를 읽지만 일부 계획에는 `1 + 3 * ...`, `until:4` 같은 3프레임 가정이 남는다. 현재 설정 3에서는 이 사실만으로 오류라고 할 수 없지만 그룹 크기가 바뀌면 계획이 어긋날 위험이 있다.
- SK.on=false가 검토 대상 설정이다. 어댑터 단위시험 통과는 대회 당일 새 스킬의 실제 물리·규칙에 대한 검증을 대신하지 않는다.
- CPU 제한/인위적 고부하를 통제한 별도 스트레스 경기, 모든 상대의 브라우저 경기, 비공개 운영 서버에서의 제출 검증은 수행하지 않았다.

## 권장 수정·재검증 순서

1. F4의 null 검사와 실패 전달을 먼저 고쳐 이후 검증 결과를 신뢰할 수 있게 한다.
2. F2 착지 등호 경계를 두 예측기에서 동시에 수정하고 최소 재현이 일치하는지 확인한다.
3. F1의 속도 복원을 정수 상태 전이 기반으로 수정한다. 이 변경은 점프 공격 판단 전반에 영향을 주므로 작은 패치로 분리한다.
4. F3에서 누운 상대의 몸 접촉을 유지한다. 기존 킬 판정이 얼마나 바뀌는지 기록한다.
5. 각 봇 변경마다 기존 기준 파일과 좌우 대결하고 수치·p99·max를 기록한다. 이 저장소에 반영한다면 `npm run duel`과 해당 게이트를 실행하고 `docs/DECISIONS.md`에 남긴 뒤 커밋한다. 기준보다 나쁘면 채택하지 않는다.
6. 수정 후보를 같은 공식 엔진·양쪽 브라우저 Worker에서 재검증한다. 원인 미확정인 좌우 차이와 40ms 스파이크는 별도 항목으로 추적한다.

v12도 같은 예측 코드를 공유하므로 단순히 v12로 되돌리는 것으로 F1~F3이 해결된다고 볼 수 없다. 지금 확인된 성능 여유에서는 대규모 최적화나 전략 재설계보다 위 국소 정확성 수정의 우선순위가 높다. 다만 수정의 경기력 이득은 아직 측정하지 않았다.

## 재현 경로

현재 작업 폴더는 `C:/leonyi-bot/.tmp/final-review-20260905`이고, 그 안의 `official`은 위에 명시한 공식 커밋이다. 제공 `competition/tools/bot-dev`를 `official/bot-dev`로 연결해 사용했고 필요한 상대 파일을 `official/src/code-here`에 두었다. 기존 로컬 의존성을 재사용했으며 새 npm 의존성을 추가하지 않았다.
