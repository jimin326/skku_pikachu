# Lion_Eating_Bank_v2.js — 세 봇을 합친 팀 봇 설명서

> 한 줄 요약: **OurBot_v11의 썬더 서브** + **Sajamokneun_v3_2의 탐색 랠리(내 서브, 썬더 안 되는 위상)** + **AdaptiveCounter_v5_2의 리시브/랠리/수비(그 외 전부)**.
> 세 파일은 바이트 단위 그대로 들어 있고(§1·§2·§3), 맨 아래 §4 오케스트레이터가 틱마다 "누구 출력을 내보낼지"만 고른다.

이 문서는 세 원본을 각각 쓴 사람이 "내 코드가 어디에, 어떤 조건에서 쓰이는지"와 "당일에 뭘 만져야 하는지"를 알 수 있게 쓴 것이다. 근거 수치는 전부 `tools/sim_real.mjs`(실게임 규약 재현: 랜덤 서브, 10점 경기, 입력 지연 1프레임, 시드 고정)로 2026-09-02에 잰 것.

## 1. 왜 이렇게 나눴나 — 각 파트가 어디서 최선인지 실측

랠리를 "누가 서브했나 × 위상(tick 격자)"으로 쪼개서 세 봇을 비교했다.

| 상황 | 최선 | 근거 (랠리 승률) |
|---|---|---|
| 내 서브, 썬더 가능 위상 (3위상 중 2개) | **OurBot_v11 썬더** | 734/734 즉시 득점. 상대가 개입 불가능한 물리 기술 |
| 내 서브, 썬더 불가 위상 (ph0) | **Sajamokneun_v3_2** (그 랠리 끝까지) | vs AC 82% / vs Saja 91% / vs v11 79% (AC 코어가 서브하면 35 / 66 / 89) |
| 상대 서브 + 그 외 전부 | **AdaptiveCounter_v5_2** | 상대서브 랠리 vs AC 68% — v11의 일반 로직은 6%, Saja는 9~15% |

- 썬더는 발동 위상이 정해져 있고, 썬더 랠리 길이가 고정(78/92프레임)+라운드 간 41프레임이라 **썬더 다음 내 서브는 항상 썬더 불가 위상**이다. 그래서 내 서브의 약 절반이 ph0이고, ph0 서브 품질이 생각보다 중요하다.
- Saja의 ph0 우위는 "서브 에이스"가 아니다. 서브(로브)로 시작하는 245프레임짜리 랠리를 탐색이 이기는 것이다. 그래서 **서브만 Saja가 치고 네트 넘어간 뒤 AC로 넘기면 무너진다**(vs Saja 91%→9%). Saja가 그 랠리를 끝까지 맡아야 한다.
- 상대별 성적(10시드×양쪽 사이드×4경기):

| 상대 | Lion_Eating_Bank_v2 | 썬더+AC만 | OurBot_v11 단독 |
|---|---|---|---|
| AdaptiveCounter_v5_2 | **78.9%** (경기 79-1) | 68.6% | 36.2% |
| Sajamokneun_v3_2 | **76.1%** (78-2) | 67.6% | 68.6% |
| OurBot_v11 | **71.0%** (76-4) | 68.6% | – |
| Jayce_v1.py (다른 팀) | 78.9% (47-1) | **90.1%** (48-0) | – |
| 내장 AI | 94.2% | 96.0% | – |

마지막 두 줄이 중요하다: **Saja 서브 랠리는 AC/Saja 계열 리시버에만 강하고 Jayce_v1에는 AC 서브보다 나쁘다**(내서브 86% vs 100%). 미지의 상대가 나오면 §4 노브 `SERVE_CORE`를 바꿔 재야 한다(아래 5절).

## 2. 파일 구조 — 내 코드는 어디 있나

```
Lion_Eating_Bank_v2.js
├─ 헤더 주석: 위 실측표와 설계 근거 요약
├─ §0 노브 (29~31행)            DEBUG, SERVE_CORE, LAT_GUARD, WIN_SCORE  + Saja의 스킬 블록(SK, applySkill)
├─ §1 Thunder  = OurBot_v11 58~207행       var Thunder = (function(){ ... return {step, kill, TH} })()
├─ §2 ACCore   = AdaptiveCounter_v5_2 전문  var ACCore  = (function(){ ... return {decide, sync} })()
├─ §3 SajaCore = Sajamokneun_v3_2 69행~끝   var SajaCore = (function(){ ... return {decide, sync} })()
└─ §4 오케스트레이터                        var M = {...}; function v12Core(s){...}; function decide(snapshot){...}
```

각 원본은 `(function(){ ... })()` 로 감싸서 **이름이 겹쳐도 서로 안 보이게** 했다(NET_X, decide, decideCore, walkTo 같은 이름이 세 파일에 다 있다). 그래서 자기 파일 안의 로직은 원본과 동일하게 동작한다. 원본에서 바꾼 것은 딱 이것뿐:

| 원본 | 바꾼 것 |
|---|---|
| OurBot_v11 (썬더 부분만) | `dfnObserve` 호출 제거, v9 폴백 자리에 `return null`(썬더가 낼 게 없으면 null), `TH.noPlan` 플래그, `kill()` 추가, 로그 문구 |
| AdaptiveCounter_v5_2 | **무수정.** 끝에 `sync(a)`(실제 적용된 입력을 `g_last_action`에 되먹임)만 노출 |
| Sajamokneun_v3_2 | 스킬 블록(§1·§2)을 파일 맨 위 §0으로 이동, `decide`의 `finishSkillAction` 두 곳을 v3 원형 반환으로 되돌림. 끝에 `sync(a,left)`(→`G.prevAct`) 노출 |

> 손으로 고치지 말고 `tools/_build_v12.mjs`를 돌려 재조립하는 것을 권한다. 세 원본 파일에서 위 수정을 **앵커 검증(정확히 1회 일치)** 후 자동 적용해 이 파일을 다시 만든다. 원본이 갱신되면 `node --no-warnings _build_v12.mjs` 한 번이면 된다.

## 3. 틱마다 무슨 일이 일어나나 (§4 `v12Core`)

```
decide(snapshot)
 │  (예외가 나면 중립 {0,0,0}; 마지막에 Saja 스킬 블록 applySkill을 한 번 씌움)
 ▼
(1) 지연 증거 갱신      직전 두 출력의 x가 다를 때 3프레임 변위로 "지연 1프레임인가 2프레임인가" 증거를 센다 (이동 없이 관찰만)
(2) 게임 종료 가드      score.self 또는 opp ≥ WIN_SCORE → 중립 출력   ← 다음 경기 첫 랠리에 다이빙/점프 입력이 남는 사고 방지
(3) 새 랠리 감지        rallyFrameCount 감소 또는 점수합 변화 → mode='AC', myServe=false
    내 서브 감지        정규화 좌표에서 공이 (56, y≤6), vx=0 이면 myServe=true
(4) 썬더                t = Thunder.step(s)   (썬더 가능 위상이면 시퀀스 입력, 아니면 null)
                        첫 틱에 내 위치가 시작점(x=36, 지상)이 아니면 → 이 랠리 썬더 포기
                        LAT_GUARD: 지연 2프레임 증거 > 1프레임 증거면 → 썬더 포기 (2프레임이면 썬더는 0/151로 자멸)
(5) 그림자 호출         aAC = ACCore.decide(s), aSJ = SajaCore.decide(s)   ← 매 틱 둘 다 호출해서 내부 상태(접촉 수, 상대 학습 등)를 살려둔다. 비용 0.5ms
(6) 출력 선택           t 있으면 → t (썬더)
                        내 서브 랠리인데 썬더가 안 냈으면(불가 위상/포기) → mode = SERVE_CORE ('SAJA'면 Saja가 그 랠리 끝까지)
                        그 외 → AC
(7) fin(a)              선택된 입력을 두 코어에 sync(a)로 되먹이고(지연 보정용 '직전 적용 입력'), 지연 증거용 상태 저장 후 반환
```

한 랠리 안에서 모드는 바뀌지 않는다(썬더→코어 전환은 썬더가 포기/종료했을 때 한 번뿐).

## 4. 합칠 때 실제로 터졌던 것들 (가드가 있는 이유)

1. **경기 경계 잔류 입력** — 실게임은 Apply당 `PikaBotInput` 하나를 재사용하고, 경기가 끝나도 211프레임 동안 봇을 호출한다. 공이 죽어 있으니 AC는 그 공으로 다이빙/점프를 내고, 그 입력이 다음 경기 첫 랠리 1~3프레임에 실행돼 썬더 시작 위치가 깨진다. 4경기 연속 벤치에서 썬더 실패가 **전부 2번째 이후 경기의 첫 랠리**였다(22/325). → (2)번 가드 + (4)번 시작위치 검사로 0건. 매 경기 재Apply하면 원래 안 생기는 문제.
2. **지연 2프레임** — 브라우저가 느려 워커 응답이 2프레임 뒤에 적용되면 썬더는 한 번도 안 된다(내서브 16%). (1)번 수동 추정기가 이를 감지해 썬더 대신 일반 서브로 간다(vs AC 34→44%). 지연 1프레임에서는 결과에 전혀 영향 없음(수치 동일 확인). "움직여서 재는" 능동 프로브는 지터 상황에서 손해라 넣지 않았다.
3. **결정적 봇끼리의 분산** — 우리 봇들은 난수를 안 써서 같은 상황이면 같은 랠리가 반복된다. 그래서 승률이 시드/이력에 따라 ±10pp 흔들린다. **3시드로 작은 차이를 판정하지 말 것.** 10시드가 기준.

넣어보고 **버린 것**(실측 손해/무익): AC 코어 좌우 미러 정규화(−2~−8pp), AC v5_1 코어, v11의 상황키 적응수비(DFN), Saja 리치 모델 조각, 궤적 자기검증, 능동 지연 프로브.

## 5. 당일 체크리스트 (§0 노브)

| 노브 | 기본 | 언제 바꾸나 |
|---|---|---|
| `WIN_SCORE` | 10 | **승리 점수가 10이 아니면 반드시 수정.** 이 점수부터 중립 출력이므로 틀리면 경기 중에 멈춘다 |
| `SERVE_CORE` | `'SAJA'` | 새 상대 파일을 받으면 `'SAJA'`/`'AC'` 둘 다 벤치해서 나은 쪽. Jayce_v1처럼 Saja 로브 서브를 잘 받는 상대면 `'AC'` |
| `LAT_GUARD` | 1 | 끌 이유 거의 없음. F12에 "썬더 포기: 지연 2프레임 증거"가 뜨면 그 머신은 느린 것 |
| `SK` | off | 당일 스킬 규칙이 나오면 Saja 스킬 블록 §1 일곱 줄만 채운다(경로·만충값·발동 여부). 최종 출력에 자동 적용 |
| `DEBUG` | true | F12 로그. 대회 제출 시 false로 |
| (AC 내부) `ADAPT_CFG.MAX_BLEND` | 0.62 | AC의 적응 수비 강도. **탐색형 상대(Saja처럼 매 틱 우리 위치를 보고 조준)에게는 0이 훨씬 낫고**(vs Saja 76→96%), AC/Jayce류엔 켜는 게 낫다(vs AC 79 vs 69). §2 안에 있음 |

**F12 로그로 상태 읽기**
- `[Thunder LEFT] 썬더 발동 phase=…` — 썬더 시퀀스 시작. 안 뜨는 내 서브는 불가 위상.
- `[v12 LEFT] 내 서브 랠리(무썬더 위상) -> SAJA 코어` — Saja가 그 랠리를 맡음.
- `[v12 …] 썬더 포기: 시작 위치 아님 / 지연 2프레임 증거 a > b` — 가드 발동. 자주 뜨면 원인(재Apply 안 함 / 느린 머신) 확인.
- `[v12 …] 새 스냅샷 필드: …` — 첫 틱에 규약에 없는 필드(게이지 등)가 있으면 여기 찍힌다.

ME=Lion_Eating_Bank_v2.js OPP=AdaptiveCounter_v5_2.js node --no-warnings _v12_bench.mjs    # 기준 벤치 (OPP를 바꿔가며)

출력의 `내서브 위상×모드 {"ph0S":[승,패],"ph1T":…,"ph2T":…}` 에서 `T`=썬더, `S`=Saja, `-`=AC. 썬더(`T`) 패배가 0이 아니면 뭔가 깨진 것.
합격선: 10시드 vs AC ≥76% / vs Saja ≥73% / vs v11 ≥68%, 썬더 패배 0, 예외 0, LAT=2 vs AC ≥40%, decide p99 < 5ms (실측 평균 0.5ms, max 7ms).

## 7. 알려진 한계와 다음 할 일

- 적응 수비와 서브 코어 선택은 **상대 유형에 따라 답이 갈리는 노브**다. 랠리가 결정적 대본이라 "ph0 내 서브 랠리를 한 번 지면 다음 ph0에서 SAJA↔AC를 바꾸는" 자동 선택(lose-shift)이 프로토타입에서 상대별 최선에 2~4pp 차로 붙었다(평균 81.2%, 고정 SAJA 79.8, 고정 AC 78.2). 아직 파일에는 안 넣었다.
- 썬더 자체는 상대가 못 막는다: 30점 경기에서 상대(AC 코어)가 100개 이상 표본으로 학습해도 40/40. 학습된 예측 착지점(x≈290)이 썬더 낙하점(223)과 멀기 때문.
- 지연 2프레임 상시 환경에서는 어떤 튜닝도 썬더를 살릴 수 없다. 가드는 손실을 줄일 뿐.
